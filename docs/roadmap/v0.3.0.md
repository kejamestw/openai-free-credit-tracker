# v0.3.0 執行與驗收計畫

> 規劃聲明：本文件是可調整的規劃草案，不構成功能、日期或上游 OpenAI 規則的承諾；實際發布範圍以對應 Release Milestone 與已完成的驗收紀錄為準。

## 版本資料

- 狀態：未開始
- 版本主題：歷史、趨勢、匯出與多專案版
- 前置版本：[v0.2.1](v0.2.1.md)
- 建議工期：單人 10–15 個工作天
- 發布產物：歷史資料庫 schema v1、趨勢 UI、CSV／JSON export schema

## 版本目標

把單次「今日查詢」升級為可重複收集、可追溯且可匯出的本機用量資料。資料庫以 UTC bucket 為基準，支援專案維度、重複同步去重、每日趨勢及 CSV／JSON 匯出。

## 成功結果

使用者可以查看至少最近 30 天的每日用量、依專案篩選、重新同步而不重複計數，並匯出具有固定 schema 的 CSV 或 JSON。程式升級、重啟或暫時離線不會破壞既有歷史資料。

## 資料契約 v1

建議至少包含下列實體：

```text
schema_migrations(version, applied_at)
projects(project_key, project_id_encrypted_or_private, display_name, first_seen_at, last_seen_at)
usage_buckets(bucket_start_utc, bucket_end_utc, project_key, model, service_tier,
              input_tokens, cached_input_tokens, output_tokens, request_count,
              catalog_version, collected_at)
collection_runs(run_id, requested_start_utc, requested_end_utc, started_at, finished_at,
                status, pages_fetched, error_code)
```

`usage_buckets` 的唯一鍵必須能讓相同 API bucket 重跑時執行 upsert，而不是追加重複資料。所有時間以 UTC 儲存；UI 可另外顯示本地時間，但不得改變 quota day 的歸屬。

## 執行計畫

### 1. 儲存層

- [ ] `V030-001` 建立 database service，所有 SQLite connection、transaction 與 migration 經由同一入口。
- [ ] `V030-002` 建立 schema v1 與 migration table；migration 必須可重複檢查且不可默默跳過失敗。
- [ ] `V030-003` 啟用 foreign key、busy timeout 與適合單機應用的 journal 策略。
- [ ] `V030-004` 定義 bucket 唯一鍵和 upsert，確保重新同步不重複計數。
- [ ] `V030-005` `collection_runs` 只記錄去敏感化狀態；錯誤不得包含 Admin Key 或原始 API body。
- [ ] `V030-006` 啟動時執行 integrity check；失敗時停止寫入、保留原檔並提供備份／修復流程。
- [ ] `V030-007` 提供一致性 snapshot backup，不直接複製正在寫入中的不完整 DB。

### 2. 同步與多專案

- [ ] `V030-010` 將目前 Usage 查詢的 `project_id` 保留到 domain model 與 storage，不在彙總階段丟棄。
- [ ] `V030-011` 支援日期範圍切片、pagination、重試與中途失敗續跑。
- [ ] `V030-012` 預設首次同步最近 30 個完整／當前 UTC 日，並顯示請求進度。
- [ ] `V030-013` 同一範圍重跑使用 upsert；API 修正舊 bucket 時本機值應被更新。
- [ ] `V030-014` 為找不到 Project ID 的資料建立明確 `unattributed` bucket。
- [ ] `V030-015` Project 顯示名稱與實際 ID 分離；一般 UI 可顯示名稱，診斷畫面預設遮罩 ID。
- [ ] `V030-016` 同步失敗保留已完整提交的日期，不把部分頁面標記為完整成功。

### 3. 查詢與每日趨勢

- [ ] `V030-020` 建立 daily aggregation query，以 `00:00:00Z` 至下一日為固定日界線。
- [ ] `V030-021` 支援全部專案、單一專案與未歸屬資料篩選。
- [ ] `V030-022` 趨勢圖至少顯示兩個免費群組、其他 tokens 與資料完整性狀態。
- [ ] `V030-023` 日期範圍提供 7、30、90 天及自訂區間；空資料不畫成 0 用量而誤導使用者。
- [ ] `V030-024` 本地圖表資源隨應用程式打包，不依賴第三方 CDN。
- [ ] `V030-025` 大量資料查詢有上限與索引，30 天及 365 天資料量需符合效能門檻。
- [ ] `V030-026` UI 顯示最後成功同步時間、失敗區段和目前資料是否完整。

### 4. 匯出

- [ ] `V030-030` 定義 CSV schema v1 的欄位名稱、固定順序、UTF-8 編碼、換行與數字格式。
- [ ] `V030-031` 定義 JSON export envelope，包含 `schema_version`、`generated_at`、filters、time zone 與 records。
- [ ] `V030-032` 匯出使用與畫面相同的日期／專案 filter，但不得只匯出圖表降採樣值。
- [ ] `V030-033` CSV 防止 spreadsheet formula injection；以 `=`, `+`, `-`, `@` 開頭的文字欄位需安全處理。
- [ ] `V030-034` 匯出前讓使用者選擇 Project ID 顯示、遮罩或排除；預設遮罩。
- [ ] `V030-035` 使用 atomic file write；取消或失敗不得留下看似完整的半份匯出檔。
- [ ] `V030-036` 建立 golden export fixtures，固定 schema 與欄位順序。

### 5. Retention 與使用者控制

- [ ] `V030-040` 設定歷史保留天數，預設保留且不自動刪除；若啟用清理需顯示 cutoff。
- [ ] `V030-041` 手動刪除歷史資料前顯示範圍、筆數與不可復原警告，並要求二次確認。
- [ ] `V030-042` 提供「開啟資料位置」「建立備份」「檢查完整性」操作。

## 驗收案例

### `AC-030-01` 首次 30 天同步（P0）

1. 使用空白資料庫與匿名多專案 fixture 啟動。
2. 執行預設同步。
3. 檢查 collection run、DB rows、每日彙總與 UI。

預期：每一個完整 bucket 僅保存一次；UTC 日界線正確；專案可篩選；UI 顯示同步完成與時間。

### `AC-030-02` Idempotent 重新同步（P0）

1. 對相同 30 天資料連續同步三次。
2. 第三次讓 fixture 修改其中一個既有 bucket。

預期：前兩次 row count 與總量不變；第三次只更新對應 bucket；不存在重複計數。

### `AC-030-03` 部分失敗與續跑（P0）

1. 在日期範圍中間模擬下一頁 timeout。
2. 關閉並重新啟動程式，再執行同步。

預期：失敗日期不標示完整；已提交完整日期保留；續跑後資料完整且沒有重複。

### `AC-030-04` 多專案隔離（P0）

1. 匯入至少三個專案及一組 unattributed fixture。
2. 依序選擇各專案、全部專案與 unattributed。

預期：圖表、合計與匯出完全符合 filter；專案 A 的 view 不包含 B；遮罩 ID 政策正確。

### `AC-030-05` CSV／JSON 匯出（P0）

1. 選定日期與專案 filter。
2. 分別匯出 CSV 和 JSON。
3. 以 parser 重新讀取並與 DB query 結果比較。

預期：record count 和數值一致；schema version 正確；UTF-8 可讀；CSV 無公式注入；預設不暴露完整 Project ID。

### `AC-030-06` 資料庫損壞（P0）

1. 備份 DB 後，在測試副本製造損壞。
2. 啟動程式並嘗試同步。

預期：程式偵測損壞並停止寫入；不覆寫原檔；UI 提供備份／修復指引；Web UI 仍能顯示安全錯誤頁。

### `AC-030-07` 效能（P1）

1. 載入等價 365 天、100 個專案的合成資料。
2. 執行 30 天全專案、365 天單專案查詢與完整匯出。

預期：30 天 UI query 在目標開發硬體 1 秒內完成；365 天 query 在 3 秒內完成；匯出過程有進度且 UI 不失去回應。

## 回復策略

- Migration 前建立一致性 DB backup；migration 失敗時保持舊 DB 不變。
- 新版應用程式若建立不可逆 schema，不允許直接用舊版開啟；需提供 export／restore 路徑。
- 同步錯誤以 transaction 隔離，不刪除先前成功資料。
- 匯出失敗只清理本次暫存檔，不影響 DB。
